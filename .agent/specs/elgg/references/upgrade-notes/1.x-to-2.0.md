# Plugin Upgrade Notes: 1.x to 2.0

Delta guidance for updating Elgg plugins from any 1.x release to 2.0,
distilled from
<https://learn.elgg.org/en/stable/appendix/upgrade-notes/1.x-to-2.0.html>.
2.0 is the largest transition in the series: composer-based installs,
canonical view names, AMD JavaScript, PDO MySQL, and a long list of
removals.

## Composer-based installation

Elgg is now installed as a composer dependency instead of at the document
root. `elgg_get_root_path()` and `$CONFIG->path` return the application
root, which is not necessarily Elgg core's root (typically
`vendor/elgg/elgg/`).

Do not access core files from a plugin by filesystem path — you cannot rely
on core's location; in particular, do not load `engine/start.php`. To boot
Elgg manually, use `Elgg\Application`:

```php
// boot Elgg in mod/myplugin/foo.php
require_once dirname(dirname(__DIR__)) . '/vendor/autoload.php';
\Elgg\Application::start();
```

Use this sparingly; prefer standard routing so public URLs and the
filesystem layout stay decoupled. Do not read `_graphics` files directly —
serve them through views: `echo elgg_view('elgg_sprites.png');`.

## Cacheable views must have a file extension

Cacheable view names must end in a file extension so assets can be served
directly from disk for performance (cached resources are browsable under
`dataroot/views_simplecache`):

- Bad: `my/cool/template`
- Good: `my/cool/template.html`

Assets are now cached by `"$viewtype/$view"` instead of
`md5("$viewtype|$view")`, so extensionless cacheable views can conflict with
directories.

## jQuery upgraded to ^2.1.4, jquery-migrate dropped

jQuery 2.x is API-compatible with 1.x but drops IE8- support, which Elgg no
longer supported anyway. See <http://jquery.com/upgrade-guide/1.9/> for
moving off jquery-migrate. To add it back instead, register and load it in
the plugin's init and define a `jquery-migrate.js` view containing the
script contents:

```php
elgg_register_js('jquery-migrate', elgg_get_simplecache_url('jquery-migrate.js'), 'head');
elgg_load_js('jquery-migrate');
```

## JS and CSS views moved out of `js/` and `css/`

They were also given `.js`/`.css` extensions where missing:

| Old view | New view |
| :--- | :--- |
| `js/view` | `view.js` |
| `js/other.js` | `other.js` |
| `css/view` | `view.css` |
| `css/other.css` | `other.css` |
| `js/img.png` | `img.png` |

The benefit is co-location: a template (`view.php`) can keep its CSS/JS
dependencies next to it (`view.css`, `view.js`). The change is as
backwards-compatible as possible, so view references need not be updated
right away, but move views to their canonical locations when possible.

Gotchas:

- The `view_vars, $view_name` and `view, $view_name` hooks operate on the
  *canonical* view name (`elgg.css`, not `css/elgg`).
- `view, all` handlers that check individual view names may never match:
  `css/elgg` was aliased to `elgg.css`, and no canonical views start with
  `css/` anymore.

## `fxp/composer-asset-plugin` required for source installs

Run `composer global require fxp/composer-asset-plugin` *before*
`composer install` or `composer create-project`, or the `bower-asset/*`
packages are not recognized and composer fails with
`Package fxp/composer-asset-plugin not found`.

## All scripts moved to bottom of page

Test plugins **with the JavaScript error console visible**. For
performance, Elgg no longer supports `script` elements in the `head`
element or in HTML views; `elgg_register_js` loads all scripts at the end
of the `body` element. Convert inline scripts to AMD or to external scripts
loaded with `elgg_load_js`.

Early in the page, Elgg provides a shim of the RequireJS `require()`
function that queues code until the AMD `elgg` and `jQuery` modules are
defined — a straightforward way to convert many inline scripts. Inline code
that fails because the stack is not yet loaded:

```html
<script>
$(function () {
    // code using $ and elgg
});
</script>
```

The `require()` form works in Elgg 2.0:

```html
<script>
require(['elgg', 'jquery'], function (elgg, $) {
    $(function () {
        // code using $ and elgg
    });
});
</script>
```

## Attribute formatter drops underscored keys

`elgg_format_attributes()` (and all APIs that use it) now filter out
attributes whose name contains an underscore. Attributes beginning with
`data-` are not removed.

## Breadcrumbs

Breadcrumb display now removes the last item if it does not contain a link.
To restore the previous behavior, replace the `elgg_prepare_breadcrumbs`
hook handler with your own:

```php
elgg_unregister_plugin_hook_handler('prepare', 'breadcrumbs', 'elgg_prepare_breadcrumbs');
elgg_register_plugin_hook_handler('prepare', 'breadcrumbs', 'myplugin_prepare_breadcrumbs');

function myplugin_prepare_breadcrumbs($hook, $type, $breadcrumbs, $params) {
    // just apply excerpt to titles
    foreach (array_keys($breadcrumbs) as $i) {
        $breadcrumbs[$i]['title'] = elgg_get_excerpt($breadcrumbs[$i]['title'], 100);
    }
    return $breadcrumbs;
}
```

## Query callbacks must be valid callables

Use only valid *callable* values for the "callback" argument/options in the
API. Querying functions — including `elgg_get_entities()`, `get_data()`,
and many more — throw a `RuntimeException` when `is_callable()` returns
`false` for the given callback value.

## Comments plugin hook

Plugins can return an empty string from the `'comments', $entity_type` hook
to override the default comments component view. To force the default
comments component, the handler must return `false` — handlers that used
empty strings to force the default need updating.

## Container permissions hook

When an entity is created, the `container_permissions_check` hook is now
almost always called once, with `$params['container']` being the entity's
correct container (e.g. a group). Before 2.0 the hook was called twice when
the container was not the owner — the first call passed the owner as
`$params['container']`, which could confuse handlers — but that first check
is bypassed when the owner is the logged-in user.

## Relationship events fire once

The "create" and "delete" relationship events are now fired only once, with
`"relationship"` as the object type. Listening for `"create", "member"` or
`"delete", "member"` no longer captures group membership additions and
removals; use `"create", "relationship"` or `"delete", "relationship"`.

## Discussion moved to its own plugin

The `object, groupforumtopic` subtype has been replaced with
`object, discussion`; upgrade plugins that use or alter the old discussion
feature to the new subtype. Nothing changes from the group owners' point of
view: discussion is still a group tool and all old discussions are intact.

## Login-over-HTTPS feature dropped

For security and performance, serve all pages over HTTPS by switching the
scheme in the site's wwwroot to `https` in the advanced settings
(`/admin/settings/advanced`).

## ext/mysql replaced by PDO MySQL

Elgg now uses a `PDO_MYSQL` connection and no longer uses any ext/mysql
functions. Code using `mysql_*` functions and implicitly relying on an open
connection will fail.

Callables provided as `$handler` to `execute_delayed_write_query()` and
`execute_delayed_read_query()` now receive a
`\Doctrine\DBAL\Driver\Statement` object where they formerly received an
ext/mysql result resource.

## Event/hook calling order may change

The `all` wildcard no longer affects the order handlers are called in. To
ensure a handler runs last, give it the highest priority of all matching
handlers; to run first, the lowest. Handlers registered with the same
priority run in registration order. To emulate prior behavior, core
handlers registered with `all` were raised in priority, so some handlers
will most likely be called in a different order.

## `export/` URLs removed

Elgg no longer provides the `export/` endpoint for exposing entity data.

## Icons migrated to Font Awesome

Elgg's sprites and most CSS classes beginning with `elgg-icon-`
[have been removed](https://github.com/Elgg/Elgg/pull/8578/files#diff-b3912b37ca7bd6c53a2968ccb6c22a94L22).
Usage of `elgg_view_icon()` is backward compatible, but static HTML using
the `elgg-icon` classes must be updated to the new markup.

## `elgg-menu-site` z-index raised

The `elgg-menu-site` z-index increased from 1 to 50 so content-area
elements can use z-index without the "More" site menu dropdown rendering
behind them. Adjust the z-index in any override of the class or of
`views/default/elements/navigation.css`.

## `input/autocomplete` view

Plugins overriding the `input/autocomplete` view must include the source
URL in the input element's `data-source` attribute, require the new
`elgg/autocomplete` AMD module, and call its `init` method. The 1.x
`elgg.autocomplete` JavaScript library is no longer used.

## Email sent through Zend\Mail

Elgg 2.0 uses the `Zend\Mail` library to send email. Edge cases may differ
from 1.x — test email notifications carefully when upgrading.

## Label elements added to core views

These views received `label` elements around some input fields; check
plugin/theme overrides for the new content:

- `views/default/core/river/filter.php`
- `views/default/forms/admin/plugins/filter.php`
- `views/default/forms/admin/plugins/sort.php`
- `views/default/forms/login.php`

## Bundled plugin changes

**Aalborg Theme**: `page/elements/navbar` now uses a Font Awesome icon for
the mobile menu selector instead of an image; the `bars.png` image and its
supporting CSS were removed — update themes accordingly.

**Likes**: objects are no longer likable by default. Register a handler to
permit the annotation, or more simply register for the `likes:is_likable`
hook (`<type>:<subtype>`) and return true:

```php
elgg_register_plugin_hook_handler('likes:is_likable', 'object:mysubtype', 'Elgg\Values::getTrue');
```

As before, the `permissions_check:annotate` hook is still called and may be
used to override default behavior.

**Messages**: if you removed or replaced the `messages_notifier` handler to
hide or alter the inbox icon, do the same for the topbar menu handler
`messages_register_topbar` — `messages_notifier` no longer adds the menu
link. Messages no longer get the `msg` metadata on creation, so it cannot
be relied on.

**Blog, Bookmarks, File**: the 'Mine' and 'Friends' listings now list all
blogs/bookmarks/files owned by the users, including those created in
groups.

## Removed plugin hooks, actions, views, and libraries

- Hook `[display, view]` — alter view output through the view plugin hook
  instead.
- Action `widgets/upgrade`.
- View `forms/admin/plugins/change_state`.
- Library `elgg:markdown` — Elgg no longer provides a markdown
  implementation; you must provide your own.

## Removed view variables

The view system no longer injects these into the scope during rendering:

- `$vars['url']` — replace with `elgg_get_site_url()`
- `$vars['user']` — replace with `elgg_get_logged_in_user_entity()`
- `$vars['config']` and `$CONFIG` — use `elgg_get_config()` and
  `elgg_set_config()`

Workarounds for very old views are no longer performed; make these changes:

- Set `$vars['full_view']` instead of `$vars['full']`.
- Set `$vars['name']` instead of `$vars['internalname']`.
- Set `$vars['id']` instead of `$vars['internalid']`.

## View selection via properties removed

The `$entity->view` metadata no longer specifies the view used to render in
`elgg_view_entity()`; likewise `$annotation->view` no longer has an effect
in `elgg_view_annotation()`.

## Viewtype is static after the initial call

Use `elgg_set_viewtype()` to set the viewtype at runtime. Although the
`view` input and `$CONFIG->view` are still checked initially, this happens
only once per request.

## Deprecations

Reading or writing metadata keys starting with `filestore::` on `ElggFile`
objects is deprecated. In Elgg 3.0 this metadata is deleted if it points to
the current data root path, so few file objects will have it. Use
`ElggFile::setFilestore` only if files need to be stored in a custom
location.

This is not the only deprecation in Elgg 2.0 — watch site error logs.
