# Plugin Upgrade Notes: 2.x to 3.0

Delta guidance for updating Elgg plugins from 2.x to 3.0, distilled from
<https://learn.elgg.org/en/stable/appendix/upgrade-notes/2.x-to-3.0.html>.
This is the largest transition in the series: it raises the PHP requirement,
removes the multi-site concept and all entity subtables, denormalizes
subtypes and metastrings, replaces raw SQL query options with a
`QueryBuilder` abstraction, introduces named routes and a dependency
injection container, and removes or deprecates hundreds of APIs.

## Detail references

Exhaustive enumerations distilled from this transition live in the
`2.x-to-3.0/` directory next to this file; load them on demand when auditing
a specific removal.

- `2.x-to-3.0/removed-views.md` — all 99 removed views, grouped thematically
- `2.x-to-3.0/removed-functions-methods.md` — every removed function and
  method, grouped thematically, with replacements

## PHP 7.0 is now required

PHP 5.6 is reaching end of life; PHP 7.0 is now required to install and run
Elgg.

## The `$CONFIG` global

The global `$CONFIG` is now a proxy for Elgg's configuration container.
Audit every usage and replace it with `elgg_get_config()` and
`elgg_set_config()`, as recommended since Elgg 1.9. Direct modification of
array properties fails with a NOTICE, e.g. `$CONFIG->cool_fruit[] = 'Pear';`.
`$CONFIG` is no longer available as a local variable inside plugin
`start.php` files.

## Removed views

99 views were removed across layouts, resources, river, search,
notifications, groups and friends, navigation, and bundled assets. The full
enumeration, with replacements, is in `2.x-to-3.0/removed-views.md`.
Highlights: all `page/layouts/*` variants consolidate into
`page/layouts/default`; `page/elements/by_line` is replaced by
`object/elements/imprint`, `output/checkboxes` by `output/tags`, and
`river/item` by `elgg_view_river_item()`; every discussion-reply view is
gone because replies migrated to comments.

## Removed functions and methods

156 functions, methods, and classes were removed, each with its replacement
where one exists; the full enumeration, grouped thematically, is in
`2.x-to-3.0/removed-functions-methods.md`. Highlights: every function in
`engine/lib/deprecated-1.9.php` and `engine/lib/deprecated-1.10.php` is
gone; the entity subtype table API is replaced by
`elgg_set_entity_class()` and `elgg_get_entity_class()`; the standalone
cache classes and the `Elgg\Cache\Pool` interface are consolidated into a
single cache API layer; and the system log functions moved into the
`system_log` plugin under new names rather than being dropped outright.

## Database schema changes

- Storage engine changes from MyISAM to InnoDB; database settings may need
  optimization for the change.
- The `datalists` table is removed; its settings are merged into the
  `config` table.
- Metastrings are denormalized: the metastrings table is gone and string
  values are stored directly in the metadata and annotation tables. The
  `msv` and `msn` table aliases are no longer available; update custom
  queries and perform your own joins instead of relying on core query
  aliases.
- The `password` and `hash` columns are removed from `users_entity`.
- The unused `geocode_cache` table is removed.
- The `subtype` column in `entities` now holds the subtype string instead of
  an ID, and the `entity_subtypes` table is dropped (see Entity subtypes).
- The `type`, `subtype`, and `access_id` columns are dropped from the
  `river` table. For queries bypassing `elgg_get_river()`, join `entities`
  on `object_guid` to check type and subtype; the access column has been
  unused for some time.
- New installations require MySQL 5.5.3 or higher and use the `utf8mb4`
  character set with LONGTEXT content columns.

## Boolean entity properties

Storage of metadata, annotation, and private setting values is aligned:
booleans are cast to integers on save (`false` as `0`, `true` as `1`). This
breaks private settings, which previously stored `false` as an empty string.
Plugins must migrate stored values from empty strings to `0` so that
`elgg_get_entities()` retrieves them with `private_setting_name_value_pairs`
containing `false`. This applies to plugin settings and entity private
settings alike.

## Metadata changes

- Metadata is no longer access controlled; restrictions on metadata created
  with restricted access will not be honored. Use annotations or entities,
  which do provide access control.
- Do not read or write the `access_id` property on `ElggMetadata` objects.
- Metadata can no longer be enabled or disabled.
- Metadata no longer has an `owner_guid`; querying by `owner_guids` is no
  longer possible, and `ElggMetadata::canEdit()` always returns `true`
  unless a plugin hook overrides it.

## Permissions and access

The user capabilities service no longer triggers permission check hooks when
permissions are checked for an admin user or with access ignored via
`elgg_set_ignore_access()`; plugins can no longer alter permissions in those
cases. `elgg_check_access_overrides()` is removed because overrides no
longer need validation. The translations for the default Elgg access levels
use new language keys.

## Multi site support removed

Partial multi-site support is completely removed. Entities no longer have a
`site_guid` attribute, so entities can no longer live on different sites;
upgrading a database that contains multiple sites fails, and the sites must
be separated into separate databases first. The `member_of_site`
relationship is gone: all related functions are removed and existing
relationships are removed during the upgrade. Setting `ElggSite::$url` has
no effect — the site URL always comes from `$CONFIG->wwwroot` in
`settings.php` or is computed by the Symfony request — and
`ElggSite::save()` fails for any site other than the main site.

## Entity subtables removed

The `sites_entity`, `groups_entity`, `objects_entity`, and `users_entity`
subtables no longer exist; all their attributes moved to metadata. Update
custom queries referencing these tables. `getOriginalAttributes()` now
returns only the base attributes of an entity, no longer the secondary
attributes.

## Friends and group access collections

- The access collections table gains a `subtype` column identifying the
  purpose of the ACL.
- User-owned collections are treated as friends collections and receive the
  `friends_collection` subtype; group ACL information moves from the
  `group_acl` metadata into the ACL subtype attribute.
- `ACCESS_FRIENDS` is migrated to a real access collection with the
  `friends` subtype; entities and annotations are updated to its new id.
  The collection is created with each user, and creating a `friends`
  relationship adds the related guid to it. Entities can no longer be saved
  or updated with the `ACCESS_FRIENDS` access id.

## Entity subtypes

Subtypes are denormalized: the `entity_subtypes` table is removed and the
`entities`.`subtype` column holds the string directly, so all API for
adding, updating, and resolving subtypes and classes is removed. Register
custom entity classes at runtime with `elgg_set_entity_class()` and
`elgg_get_entity_class()` (e.g. in a system init handler). Every entity now
must have a subtype; `user`, `group`, and `site` are added and reserved by
default.

## Custom class loading

Elgg no longer provides class registration APIs. Use PSR-0 classes in the
plugin's `classes` folder or composer autoloading instead.
`elgg_get_class_loader()`, `elgg_register_class()`, and
`elgg_register_classes()` are removed.

## Dependency injection container

Plugins can define their services in an `elgg-services.php` file at the root
of the plugin directory and attach them to Elgg's public DI container. The
`elgg()` function no longer returns the application instance but the DI
container.

## Query building

`elgg_get_entities()` now accepts all options previously spread across
`elgg_get_entities_from_metadata()`, `..._from_annotations()`,
`..._from_relationship()`, `..._from_private_settings()`, and
`..._from_access_id()`, which are deprecated, as are their
`elgg_list_entities_from_*` counterparts.

Passing raw MySQL statements in options is deprecated. Provide closures that
receive an `\Elgg\Database\QueryBuilder` and prepare statements through the
database abstraction layer — this sanitizes values through the database
driver and moves query building to testable, object-oriented code:

```php
elgg_get_entities([
    'wheres' => [
        function (\Elgg\Database\QueryBuilder $qb, $alias) {
            $joined_alias = $qb->joinMetadataTable($alias, 'guid', 'status');
            return $qb->compare(
                "$joined_alias.name",
                'in',
                ['draft', 'unsaved_draft'],
                ELGG_VALUE_STRING
            );
        },
    ],
]);
```

- `wheres` clauses take an `\Elgg\Database\Clauses\WhereClause` instance or
  a closure returning a
  `\Doctrine\DBAL\Query\Expression\CompositeExpression`; `joins`,
  `order_by`, `group_by`, and `selects` take closures returning prepared
  statements.
- The `reverse_order_by` option is removed.
- Do not rely on joined or selected table aliases: closures receive the
  selected table alias as their second argument and must perform their own
  joins.
- The private API around building raw SQL strings is removed. Anything
  marked `@access private` or `@internal` can change or disappear at any
  time; request a public equivalent through a GitHub issue instead of using
  it.

## Routing

`elgg_register_page_handler()` is deprecated in favor of named routes:
register them with `elgg_register_route()` and generate URLs with
`elgg_generate_url()`, or `elgg_generate_entity_url()` as a shortcut for
named routes that depend on entity type and subtype. All core page handlers
are removed and their logic moved to resource views. The `handler` parameter
in entity menus is deprecated in favor of named entity routes. Gatekeeper
functions are refactored into routing middleware: they no longer return
values but throw HTTP exceptions that are routed to error pages and can be
redirected to other pages via hooks.

## Labelling conventions

Entity and collection labelling follows new conventions that the routing and
navigation systems rely on:

- `item:object:blog` — singular entity label
- `collection:object:blog` — plural collection label, with `:all`, `:owner`,
  `:group`, and `:friends` variants
- `add:object:blog` / `edit:object:blog` — action labels

Plugins are advised to follow these conventions.

## Request value filtering

`set_input()` and `get_input()` no longer trim values.

## Action responses

All core and core-plugin actions now use the HTTP response functions
(`elgg_ok_response()`, `elgg_error_response()`) instead of `forward()`, so
in most cases the `forward, system` hook is no longer triggered. Influence
responses through the `response, action:<name>` hook, which targets a
specific action directly.

## New approach to page layouts

The `one_column`, `one_sidebar`, `two_sidebar`, and `content` layouts are
removed; rendering is centralized in the `default` layout, which provides
full control over layout elements via `$vars`. For backwards compatibility,
`elgg_view_layout()` calls with the old names still yield the expected
output, but plugins should switch to `default` with the updated parameter
set. Layouts are decomposed into smaller elements so themes can target
specific elements without overriding whole layouts:

- all layouts handle title and filter menus, breadcrumbs, and layout
  subviews consistently
- all layouts support multiple tabs: pass a `filter_id` parameter and other
  plugins can add tabs through the `register, menu:filter:<filter_id>` hook
  (or the default `register, menu:filter` hook when no `filter_id` is set)
- layout views and subviews receive `identifier` and `segments` of the
  rendered page
- layout parameters are available to title and filter menu hooks, letting
  resources provide context such as an `$entity` for a profile page

Plugins and themes should:

- update `elgg_view_layout()` calls to use the `default` layout
- replace the `nav` parameter with `breadcrumbs`
- update `filter` parameter usage: provide a default set of filter tabs, or
  set `filter_id` and use hooks
- remove `page/layouts/one_column`, `page/layouts/one_sidebar`,
  `page/layouts/two_sidebar`, and `page/layouts/content` views
- update usage of `page/layouts/default`, `page/layouts/error`,
  `page/layouts/elements/filter`, `page/layouts/elements/header`,
  `page/layouts/elements/footer`, and `page/elements/title`
- update `navigation/breadcrumbs` usage to pass `$vars['breadcrumbs']` to
  `elgg_get_breadcrumbs()`
- re-register `output:before, layout` hooks as
  `view_vars, page/layout/<layout_name>` and `output:after, layout` hooks
  as `view, page/layout/<layout_name>`

## View extension behaviour changed

An extended view now receives all the regular hooks (such as `view_vars`),
and view extensions can themselves be extended. All view rendering behaves
the same regardless of whether the view was used as an extension.

## JavaScript hook calling order may change

The `all` wildcard no longer influences handler call order. To run last, a
handler needs the highest priority of all matching handlers; to run first,
the lowest. Handlers registered with the same priority run in registration
order. Core handlers registered with `all` have been raised in priority to
emulate prior behaviour, so some handlers may be called in a different
order.

## Widget layout related changes

- Content is no longer drawn as part of the widget layout: wrap content in
  another layout and use the widgets layout as part of it. Pass a
  `no_widgets` parameter (string or closure) to show special content when
  the layout has no widgets.
- The `all` context is no longer supported when registering widgets;
  explicit contexts are required.

## Entity, river and menu changes

Entity and river menus show all items in a dropdown; social actions such as
liking and commenting moved to a separate social menu meant for social
actions.

- Default menu sorting changed from `text` to `priority`.
- `register` and `prepare` hooks now use the collections API; hooks keep
  working unless they perform complex operations on arrays.
- `icon` and `badge` parameters are supported on menu items; prefer them
  over a single `text` parameter, and control label, icon, and badge
  visibility with CSS instead of conditionals in menu preparation.
- All menus are wrapped in `nav.elgg-menu-container` so multiple sections
  share a single parent element, stylable with flexbox or floats.
- Menu items carry a `data-menu-item` attribute, sections
  `data-menu-section`, and containers `data-menu-name`.

Per-menu changes:

- `topbar`: an `account` item with priority 800 heads the `alt` section;
  `site_notifications` (100), `usersettings` (300), `administration` (800),
  `logout` (900), `dashboard` (100), `profile`, and `friends` are now
  children of `account`. Core items in the `default` section (`profile`,
  `friends`, `messages`) use the `icon` parameter with CSS-hidden labels —
  plugins registering visible-label items there must update their CSS.
- `entity`: the `access` item is removed; access information renders in the
  entity byline.
- `user_hover`: all items use the `icon` parameter, and the dropdown layout
  changed; update custom HTML/CSS for it.
- `widget`: the `collapse` item was removed and CSS updated accordingly.
- `title`: the profile plugin registers regular `title` menu items instead
  of using the `user_hover` actions section.
- `extras`: removed from the page layout; its items moved to other menus.
- `groups:my_status`: removed from the group profile page.
- `site_notifications`: the menu is removed; Site Notification objects use
  the entity menu for actions.
- `site`: custom items defined in the admin interface register through the
  `register, menu:site` hook; the `navigation/menu/site` view is removed
  and the `more` item is added directly to the `default` section.

## Object listing views

- `object/elements/full/body` wraps the full listing body in a
  `.elgg-listing-full-body` wrapper.
- `object/elements/full` supports `attachments` and `responses`, rendered
  after the listing body.
- Core plugin resource views no longer render comments/replies; they pass a
  `show_responses` flag to the entity view, which renders the responses and
  passes them to the full listing view. Third-party plugins must update
  their `object/<subtype>` and `resources/<handler>/view` usage.
- The full discussion view renders through `object/elements/full`.
- `object/file` passes its image (specialcontent) view as an `attachment`
  to the full listing view.

## Comments

Comment submission is AJAXed; the comment list updates automatically after
a successful submission.

- Comment notification language keys changed — check the
  `generic_comment:notification:owner:` keys.
- The `comment/save` action changed and no longer sends the notification
  directly (offloaded to the notification system); plugins that overrode
  the action should review the override to prevent double notifications.

## Entity icons

- Default icon files are re-mapped: default icons to
  `views/default/icon/default/$size.png`, user icons to
  `views/default/icon/user/default/$size.gif`, and group icons to
  `views/default/icon/group/default/$size.gif` in the groups plugin.
- Group icon files moved from `groups/<guid><size>.jpg` relative to the
  group owner's filestore directory to the location prescribed by the
  entity icon service. Stop accessing files on the filestore directly and
  use the entity icon API; an upgrade script is available via the admin
  interface.
- `ElggEntity::saveIconFromUploadedFile()`, `saveIconFromLocalFile()`, and
  `saveIconFromElggFile()` only save the `master` size; other configured
  sizes are generated on demand by `ElggEntity::getIcon()` based on the
  master icon.

## Icon glyphs

FontAwesome is upgraded to version 5.0+. Glyph rendering changed; core
handles most of it (mapping old icon names to new ones, and using the
correct prefix for brand and solid icons).

## Autocomplete (user and friends pickers)

The friends picker input renders through `input/userpicker`. Plugins
should update overridden `input/userpicker` views to support the new
`only_friends` parameter and remove friends picker CSS from their
stylesheets.

## Theme and styling changes

The Aalborg theme is no longer bundled; the default core theme is based on
Aalboard with major changes:

- topbar, navbar, and header combine into a single responsive topbar
  component
- default inner width is 1280px (80rem at 16px/rem)
- `rem` is the preferred unit over `px`
- the theme uses an 8-point grid system
- menus, layout elements, and other components use flexbox
- the reset uses normalize.css
- media queries are rewritten for a mobile-first experience
- form elements (text inputs, buttons, selects) have an equal height of
  2.5rem
- the layout header sits outside the layout columns, which are wrapped in
  `elgg-layout-columns`
- z-index values are reviewed and stacked with simple iteration
- the color scheme highlights actionable elements and reduces gray shades
- the search plugin no longer extends `page/elements/header`;
  `page/elements/topbar` renders the `search/search_box` view
- `.elgg-icon` no longer has global `font-size`, `line-height`, or `color`;
  these values inherit from parent items
- `.elgg-icon-hover` support is dropped
- user hover icons are no longer covered with a caret icon

See the Theming Principles guide
(<https://learn.elgg.org/en/stable/guides/themes.html>).

CSS views served via `/cache` URLs are pre-processed with CSS Crush: CSS
variables and other references must be defined within the same view output
(e.g. a variable defined in `elgg.css` cannot be referenced from a separate
file like `colorbox.css`).

## Layout of `.elgg-body` elements

`.elgg-body` elements no longer stretch to fill available space in block
context by default; they still clear floats and break words. Core modules
that relied on space-filling were reworked for flexbox — do the same rather
than using `overflow: hidden`.

## Likes plugin

Likes no longer uses the toggle API, so a single `likes` menu item is used.
The add/remove actions no longer return Ajax values directly; likes status
data is returned with every Ajax request that sends a `guid`. When the
count is zero, the `likes_count` menu item is hidden by adding `.hidden` to
the `li` element instead of the anchor, and it is a regular link no longer
created by the `likes/count` view.

## Notifications plugin

Rewritten for a more efficient, extendable, and scalable interface for
managing notification preferences, with simpler markup and excessive
styling and JavaScript removed. Many views and actions were dropped —
plugins extending its views or relying on its actions must be updated.

## Pages plugin

The `page_top` subtype migrated into the `page` subtype, which has its own
`ElggPage` class with an `isTopPage()` method. All pages carry a
`parent_guid` metadata value; top pages hold `0`.

## Profile plugin

All profile functionality moved out of core into the plugin — most notably
the profile field admin utility and the hook that sets up the profile
fields config data.

## Friends collections

The friends collections UI moved to its own `friends_collections` plugin.

## Data Views plugin

The Data Views plugin no longer comes bundled.

## Twitter API plugin

The `twitter_api` plugin is removed from core but still available as the
composer package `elgg/twitter_api` (~1.9); add it to the `require`
section of `composer.json` to keep using it.

## Legacy URLs plugin

The `legacy_urls` plugin is removed from core but still available as the
composer package `elgg/legacy_urls` (~2.3); add it to the `require` section
of `composer.json` to keep legacy URL support.

## User validation by email plugin

The listing view of unvalidated users moved from the plugin to Elgg core,
as did generic actions such as validate and delete.

## Discussion replies moved to comments

Discussion replies were mostly a carbon copy of comments, so all replies
migrated to comments; all related actions, hooks, events, and language keys
are removed. Discussion comments now appear under the Comments section of
Search, no longer under Discussion.

## Email delivery

For finer-grained email handling, the `email, system` hook is removed; the
new email service provides replacement hooks controlling email content,
format, and transport. `elgg_set_email_transport()` replaces the default
Sendmail transport with any `\Zend\Mail\Transport\TransportInterface`
instance (SMTP, in-memory, file). Call it early in the boot process;
deriving transport config from plugin settings on each request is
inefficient — store such settings as datalist or site config values so
they load from the boot cache.

## HtmLawed is no longer a plugin

Do not call `elgg_load_library('htmlawed')`. In the params of the
`config, htmlawed` hook, the `hook_tag` function name changed.

## Delete river items

`elgg_delete_river()`, deprecated in 2.3, is reinstated with changes:

- it accepts all `elgg_get_river()` options but requires at least one of:
  id(s), annotation_id(s), subject_guid(s), object_guid(s), target_guid(s),
  or view(s)
- `elgg_get_river()` applies a default limit, so set `limit` to `false` to
  remove all river items
- access is ignored while deleting river items
- events fire just before and after a river item is deleted

## System Log

The system log API moved out of core into the `system_log` plugin; the
`logbrowser` and `logrotate` plugins merged into it.

## Error logging

Sending `elgg_log()` output and PHP error messages to the page is only
possible via the developers plugin "Log to the screen" setting; see
`settings.example.php` for `$CONFIG->debug` usage in `settings.php`.
Debugging should generally use the xdebug extension or tail the error log.

## Translations cleanup

All plugins were scanned for unused translation keys, which were removed;
where a generic translation was available for a custom key, it was updated
to the generic one.

## Composer asset plugin no longer required

Assets load from <https://asset-packagist.org>; the FXP composer asset
plugin is no longer required when installing Elgg or updating composer
dependencies.

## Cron logs

Cron logs are stored on the filesystem (in the dataroot) instead of the
database, allowing longer output. A migration script moves the old database
values to the new location and removes them from the database.

## Miscellaneous changes

The "Allow visitors to register" and "Restrict pages to logged-in users"
settings now appear on the Basic Settings admin page.

## Unit and integration testing

Elgg's PHPUnit bootstrap handles both unit and integration tests. Never run
tests on a production site — specify database settings via environment
variables (e.g. through the `phpunit.xml` bootstrap) to prevent data loss.

- plugins implement tests by extending `\Elgg\UnitTestCase` and
  `\Elgg\IntegrationTestCase`
- the `plugins` suite autoloads tests from
  `mod/<plugin_id>/tests/phpunit/unit` and
  `mod/<plugin_id>/tests/phpunit/integration`
- enable the plugins under test before running integration tests
- `\Elgg\IntegrationTestCase` includes the `\Elgg\Seeding` trait for
  conveniently building entities and writing them to the database
- `\Elgg\UnitTestCase` uses no database but provides a mocking interface
  for defining query specs with predefined returns
- both suites run by default; select one with `phpunit --testsuite unit`,
  `--testsuite integration`, or `--testsuite plugins`
- keep `start.php` free of root-level logic and return a closure instead,
  so the test suite can build a fresh Application without losing plugin
  initialization logic
- simpletests keep working, but `ElggCoreUnitTest` method signatures
  changed: avoid `__construct`/`__destruct`; `setUp`/`tearDown` are private
  and used for internal bootstrapping — implement `up`/`down` instead
- simpletests can no longer be executed from the developers plugin admin
  interface; use `elgg-cli simpletest`
