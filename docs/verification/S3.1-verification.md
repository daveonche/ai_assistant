That the pinned release reference agrees across all three enforcement
locations, per `tests/test_release_ref_consistency.py`:

- `scripts/install.sh` — `DEFAULT_REF` and its `usage()` example URLs
- `README.md` — every documented install URL
- `tests/test_s2_1_step5.py` — the tested install command
  (`INSTALL_COMMAND`)

### Induced-failure exercise (Step 1)

`DEFAULT_REF` in `scripts/install.sh` was temporarily changed from
`v1.0.3` to `v9.9.9` and the suite re-run. Observed: `3 failed`. Each
failure message named the mismatched location and both references, for
example:

```text

bump every curl URL to v9.9.9 (the --ref example argument may keep an
older tag)
```

The installer file was restored to `v1.0.3` by the trailing `sed` in
the same command chain.

### Post-restore confirmation (Steps 1–2)

```bash
python3 -m pytest -q tests/test_release_ref_consistency.py
git --no-pager status --porcelain
```

Observed: `3 passed` and empty status output — the repository state was
clean, with no leftover edits from the induced-failure exercise.

## Summary

No inconsistency was found. All three pinned locations agree on the
currently pinned release tag, `v1.0.3`:

- `scripts/install.sh`: `readonly DEFAULT_REF="v1.0.3"` plus `v1.0.3`
  in the `usage()` example URLs
- `README.md`: every documented install URL carries `v1.0.3`
- `tests/test_s2_1_step5.py`: `INSTALL_COMMAND` pins `v1.0.3`

No remediation change was required; the remediation path itself was
demonstrated by the induced-failure exercise.
