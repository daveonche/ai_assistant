Story S6.1 Implementation Steps:

Step 1. Enable single-directory launch through the consolidated entry script
Must Support:
- The entry script lives at `.agent/start.sh` with behavior identical to the current entry script (environment bootstrap followed by handoff to the assistant launcher)
- The root-level entry script is removed from the repository
- Launching from the project root works via `./.agent/start.sh`
- The new entry script is committed with the executable bit set, so its executability is part of the repository state
Manual Verification:
- From the project root, run `./.agent/start.sh` and observe the assistant starts and behaves exactly as before
- List the project root and observe no entry script remains at the old root-level location
Prerequisite: None
Developer Notes:
- Keep the move behavior-preserving: users should notice no difference except the launch path
- Do not change bootstrap or handoff logic while relocating; this step is a relocation only
- Documentation updates for the new launch path are handled by a later story

Step 2. Enable the commit-message gate file to reside inside the assistant directory
Must Support:
- The commit-message gate file is located at `.agent/githooks/commit-msg` with its checking behavior unchanged
- The former top-level hook location no longer contains the gate file
Manual Verification:
- Inspect the repository and observe the gate file present at `.agent/githooks/commit-msg`
- Inspect the repository and observe no gate file remains at the old top-level hook location
Prerequisite: None
Developer Notes:
- This step changes only where the gate file lives; keeping the gate activated is handled by the next story
- Keep the gate's checking rules unchanged during the move

Step 3. Enable install mode to provision only the assistant directory
Must Support:
- Install mode stages exactly the `.agent/` directory into a target project root and nothing else
- Install-target detection recognizes a project by the presence of `.agent` alone
- The installed entry script's executability is recorded in the target repository's tracked file metadata, so it survives copies that do not preserve file permissions
Manual Verification:
- Run install mode against a fresh target project and observe only `.agent/` appears at the target root
- In the installed project, run `./.agent/start.sh` and observe the assistant starts without manually fixing permissions
- Inspect the installed project's tracked file metadata and observe the entry script recorded as executable
Prerequisite: Step 1 — the entry script must exist at its `.agent/` path before install mode can stage and record it
Developer Notes:
- Keep the installed set minimal so consumers receive a single self-contained directory
- Record executability in a way that does not depend on the copying process preserving permissions

Step 4. Enable update mode to refresh only the assistant directory as one reviewable change
Must Support:
- The update guard, the preview listing, and the apply path all operate on `.agent` paths only
- A refresh produces exactly one commit limited to `.agent`, which a reviewer can approve and revert as a single change
- The refresh succeeds in a consumer project that has no commits yet, recording the refresh as that project's first commit
- After a refresh, the entry script remains executable in the consumer project
Manual Verification:
- In an installed consumer project, run update mode and observe the preview lists only `.agent` paths
- Apply the refresh and observe exactly one commit touching only `.agent`; revert it and observe the project returns to its prior state
- In a freshly installed consumer project with no commit history, run update mode and observe the refresh completes and becomes the first commit
- After the refresh, run `./.agent/start.sh` in the consumer project and observe it starts without permission fixes
Prerequisite: Step 3 — update mode operates on the install layout defined in Step 3
Developer Notes:
- Aim for a refresh that is self-contained: one change, fully reviewable, fully revertable
- Treat the no-history project as a first-class case, not an edge case

Step 5. Enable green verification suites for the consolidated layout
Must Support:
- Verification suites covering the entry chain, the installer, and the tracked repository layout are updated to the new paths
- The affected suites pass end-to-end with no remaining references to the old locations
Manual Verification:
- Run the verification suites covering the entry chain, installer, and tracked layout and observe every test passes
- Search the suites for the old paths and observe no stale references remain
Prerequisite: Steps 1-4 — all layout changes must be complete before the suites are aligned
Developer Notes:
- Update the affected suites together so the whole set passes as one unit
- Remove or update lingering references to the old locations rather than leaving them dormant
