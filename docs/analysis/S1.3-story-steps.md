# Story S1.3 Implementation Steps:

Step 1. Enable launcher entry and argument forwarding
Must Support:

- A launcher entry file within the `.agent/` configuration directory that executes on the host and completes the delegation chain started by the existing host entry script.
- Accepting a debug flag that turns on verbose output.
- Forwarding all remaining user arguments, unchanged and in order, to the assistant environment launch.
- Implementing all launcher functionality using only the host runtime's built-in capabilities, with no external packages.

Manual Verification:

- Invoke the launcher through the existing host entry script with the debug flag and observe that verbose output activates.
- Invoke it with an arbitrary assistant argument and observe that the argument is passed through without alteration.
- On a host that provides only the base runtime and the container engine, confirm the launcher starts without any additional installation step.

Prerequisite: None
Developer Notes:

- Keep the entry file self-contained so it runs wherever the host runtime is present.
- Argument forwarding should preserve order and grouping exactly as received.

Step 2. Enable command tracing and debug output
Must Support:

- A single tracing routine through which every command the launcher performs is recorded before it runs.
- Verbose output that prints each traced command when the debug flag is enabled.

Manual Verification:

- Run with the debug flag enabled and observe each performed command printed before it runs.
- Run without the debug flag and confirm no trace output appears while behavior stays otherwise identical.

Prerequisite: Step 1
Developer Notes:

- Route every executed command through the tracing routine so none can bypass it.
- Record command structure only; never include secret values in trace output.

Step 3. Enable container engine availability gating
Must Support:

- A pre-launch check that confirms the container engine is available before any container lifecycle action is attempted.
- When the engine is missing, an immediate exit with a clear, actionable error and an unsuccessful result instead of a crash or partial run.

Manual Verification:

- With the engine available, start the launcher and confirm it proceeds past the check.
- Temporarily make the engine command unavailable, run the launcher, and observe an immediate, readable error stating what is missing and what to do next.

Prerequisite: Step 2
Developer Notes:

- Run the availability check as the first lifecycle action so failures surface before any long operation.
- Error text should name the missing prerequisite and the user's next action.

Step 4. Enable deterministic session container identity
Must Support:

- Container names derived deterministically from a hash of the current workspace location combined with a unique per-session identifier.
- The same workspace always producing the same name portion, while separate sessions produce distinguishable names.

Manual Verification:

- Run the launcher from the same workspace in two separate sessions and confirm the resulting container names share the workspace-derived portion but differ per session.
- Re-run within the same session and confirm the identity remains stable and predictable.

Prerequisite: Step 1
Developer Notes:

- Derive the workspace portion from the actual workspace location so identical workspaces match and different ones never collide.
- Keep the per-session identifier unique for each launch so concurrent sessions stay isolated.

Step 5. Enable container image build management
Must Support:

- Building the environment image from the container definition file stored in `.agent/` whenever the image does not exist.
- Rebuilding only when the definition has changed, and reusing the existing image otherwise.

Manual Verification:

- Remove the local image using the container engine's own tooling, run the launcher, and confirm the image is built before launch.
- Run again without changes and confirm the build is skipped; then modify the definition file and confirm the image is rebuilt.

Prerequisite: Step 3
Developer Notes:

- Keep the rebuild decision deterministic and inexpensive so repeated launches stay fast.
- The definition file's location is fixed by the story's acceptance criteria.

Step 6. Enable assistant configuration argument assembly
Must Support:

- Reading the assistant configuration files kept in `.agent/` and assembling the corresponding launch arguments.
- Combining configuration-derived arguments with the arguments the user supplied, with user arguments taking precedence where they overlap.

Manual Verification:

- Change a value in an `.agent/` configuration file, run with the debug flag, and observe the change reflected in the assembled launch arguments.
- Supply a custom assistant argument and observe it appearing alongside the configuration-derived arguments in the trace.

Prerequisite: Step 2
Developer Notes:

- Treat the configuration files as the single source of defaults; never hard-code defaults elsewhere.
- Handle absent or empty configuration gracefully by launching with sensible built-in behavior.

Step 7. Enable interactive assistant session launch
Must Support:

- Starting the environment container from the built image under the session identity, with the current workspace made available inside the container.
- Launching the assistant inside the container as an interactive session attached to the user's terminal, forwarding the assembled and user-supplied arguments.
- Returning control cleanly to the user when the assistant session ends.

Manual Verification:

- Run the launcher and confirm the assistant's interactive prompt appears and accepts input.
- Confirm the workspace contents are visible to the assistant inside the environment.
- Exit the assistant and confirm the launcher returns to the terminal without errors.

Prerequisite: Steps 4, 5, and 6
Developer Notes:

- The interactive session requires the container to remain attached to the user's terminal for input and output.
- Expose the workspace so the assistant can read and modify project files directly.

Step 8. Enable session container cleanup
Must Support:

- Stopping and removing the containers belonging to the current session when the assistant session ends or the launcher is run again.
- Leaving containers from other sessions untouched.

Manual Verification:

- Run the launcher, exit the assistant, and confirm the session container no longer exists.
- Run the launcher again and confirm no duplicate-named or orphaned containers remain and no errors occur.

Prerequisite: Step 7
Developer Notes:

- Target cleanup by the shared session identity so only this session's containers are affected.
- Aim to run cleanup even when a session ends unexpectedly so containers do not accumulate.
