Story S1.6 Implementation Steps:

Step 1. Enable the automated validation pipeline definition
Must Support:
- A pipeline definition at `.github/workflows/ci.yml` that runs automatically on every push and pull request
- Explicit, minimal pipeline permissions restricted to read-only repository content
- All reusable automation components referenced by immutable, exact identifiers with recorded versions
Manual Verification:
- Push a commit and observe the pipeline start automatically in the hosting service's automation view
- Confirm a run appears for every push without any manual triggering
- Open a pull request and confirm a run is triggered for it as well
Prerequisite: A repository containing the launcher, shell entry scripts, and container image definition (Stories S1.1–S1.5 complete)
Developer Notes:
- Keep the pipeline minimal; it should run only the validations this story requires
- Restrict permissions to the minimum the pipeline needs to operate
- Apply the project's documented pipeline conventions from the start, so the final checklist review confirms the definition rather than requiring rework

Step 2. Enable launcher source code validation in the pipeline
Must Support:
- Automated syntax and style validation of `.agent/ai_assistant.py` on every pipeline run
- Validation performed with the language's built-in checking capability alone, requiring no additional packages; introducing a stricter checker later is a new-dependency decision, not part of this step
- A detected validation error marks the overall pipeline run as failed
Manual Verification:
- Temporarily introduce a syntax error into `.agent/ai_assistant.py`, push, and confirm the run fails at this validation
- Revert the error, push, and confirm the validation passes
Prerequisite: Step 1
Developer Notes:
- Run this validation in its own stage so a failure is easy to attribute
- Add stricter checks only if they stay green on the current tree

Step 3. Enable shell script validation in the pipeline
Must Support:
- Automated static analysis of every `*.sh` script in the repository (currently `agent.sh` and `.agent/ai-assistant.sh`)
- Scripts discovered by pattern rather than a hard-coded list, so newly added scripts are covered automatically
- A detected analysis finding marks the overall pipeline run as failed
Manual Verification:
- Temporarily introduce a defect a static analyzer would flag (e.g., an unquoted variable expansion), push, and confirm the run fails
- Revert the change, push, and confirm the validation passes
Prerequisite: Step 1
Developer Notes:
- Keep this validation independent of the launcher validation so failures remain clearly attributable

Step 4. Enable container image build validation in the pipeline
Must Support:
- Automated build of the container image from `.agent/Dockerfile.aider` on every pipeline run
- The build mirrors the launcher's own image build (same definition and build inputs)
- A build failure marks the overall pipeline run as failed
Manual Verification:
- Temporarily break the image definition (e.g., an invalid base image reference), push, and confirm the build stage fails
- Revert the change, push, and confirm the build succeeds
Prerequisite: Step 1
Developer Notes:
- Keep the build inputs identical to local builds so the pipeline validates what developers actually run

Step 5. Enable end-to-end pipeline result confirmation on a clean tree
Must Support:
- A full pipeline run on the unmodified repository completes successfully with every stage green
- Each validation stage's outcome is visible in the run summary
- Any single stage failure fails the overall run and blocks merge
- A review pass against the project's documented pipeline conventions checklist, including re-verification of the immutable component references
Manual Verification:
- On a clean tree, open the latest run and confirm all validation stages report success
- Confirm the overall run status is passing and record that the immutable references still match their documented versions
Prerequisite: Steps 1–4
Developer Notes:
- Record the verified component versions in the technology stack documentation if anything changed
