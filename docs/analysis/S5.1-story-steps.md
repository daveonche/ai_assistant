# Story S5.1 Implementation Steps

Story: S5.1 - Host-Side Per-Project Configuration (Replaces Root-Config Merging)

Sprint story: `docs/sprints/sprint_5_stories.md`
Dependency report: `docs/dependencies/S5.1-dependencies.md`

## Step 1. Remove project-root configuration reading

Must Support:

- The launcher builds its assistant configuration references pointing only at the assistant's own configuration directory
- Project-root configuration files (.aider.conf.yml, .aider.model.settings.yml, .aiderignore, .aider.model.metadata.json) are never detected, read, or passed to the assistant
- All launcher behaviors unrelated to configuration reading continue to work unchanged

Manual Verification:

- Place a project-root .aider.conf.yml containing a distinctive harmless setting; launch the assistant; observe the setting has no effect on the session
- Launch in a project with no root configuration files; observe the assistant starts normally with the assistant-directory defaults

Prerequisite: None

Developer Notes:

- Remove the feature completely rather than disabling it, so no unreachable logic remains behind
- Keep every behavior unrelated to configuration reading untouched
- Focus on user objectives, not implementation

## Step 2. Enable per-project args file loading at launch

Must Support:

- A per-project args file lives at a stable host-side location outside any repository, keyed to the project's identity
- At launch, the file's entries are applied as assistant arguments: one argument token per line, blank lines and comment lines ignored, entries applied verbatim with no command-interpreter interpretation
- File entries take effect on every launch; explicitly typed command-line arguments win over file entries
- When output is an interactive terminal, a status line reports the file's path and how many entries were loaded, or a hint to create the file when none exists; no status line when output is not an interactive terminal

Manual Verification:

- Create an args file with a harmless display-type assistant argument; launch; observe the argument takes effect and the status line reports the loaded count
- Type the same argument on the command line with a different value; launch; observe the typed value wins
- Run the launcher with output redirected to a file; observe no status line appears

Prerequisite: Step 1

Developer Notes:

- The file lives in the user's home configuration area, so repository content can never create or alter it
- Keep the file format line-based and free of any command-interpreter syntax so entries stay predictable
- Reuse the project-identity calculation the launcher already uses elsewhere rather than introducing a second one

## Step 3. Enable args-file template creation

Must Support:

- A launcher flag creates the per-project args file with commented guidance when it does not exist
- An existing args file is never overwritten or modified
- The flag works even when container tooling is unavailable
- Template comments include worked examples for overriding the model-settings file and the ignore file, with guidance to: reference files under a distinctive name unlikely to exist in any repository, create the referenced file in the project root and copy the needed entries from the assistant's own copy so it is self-sufficient, and use the override only when a project genuinely needs extra or different configurations

Manual Verification:

- Run the flag in a project with no args file; observe the template is created at the reported path and contains the guidance comments
- Run the flag a second time; observe the existing file is unchanged
- On a machine without container tooling, run the flag; observe it still creates the template

Prerequisite: Step 2

Developer Notes:

- The template's purpose is to teach safe customization at the moment of first use
- Guidance should make the failure modes visible: a same-named repository file could silently satisfy a reference, and an override replaces the assistant's defaults entirely
- Focus on user objectives, not implementation

## Step 4. Enable effective-configuration display

Must Support:

- A launcher flag prints the args-file path, its contents (or a clear absence notice with the creation hint), and the effective argument order: typed command-line arguments win over file entries, which win over the assistant-directory defaults
- The flag works even when container tooling is unavailable

Manual Verification:

- Run the flag with no args file; observe the path and an absence notice pointing at the template-creation flag
- Create an args file; run the flag; observe the path, contents, and precedence explanation

Prerequisite: Step 2

Developer Notes:

- This flag is the single command that answers "what configuration is actually in effect for this project"
- Keep the output human-readable and self-explanatory
- Focus on user objectives, not implementation

## Step 5. Notify when project-root configuration files are present

Must Support:

- When any of the four known project-root configuration filenames exists, a one-line notice states the file is not read and points at the template-creation flag
- The check tests existence only; file contents are never read
- No notice appears when no such files exist

Manual Verification:

- Place a project-root .aider.conf.yml; launch; observe the one-line notice
- Remove the file; launch; observe no notice

Prerequisite: Step 1

Developer Notes:

- The notice prevents the silent-nothing experience when a repository ships configuration files the launcher deliberately ignores
- Existence checking only; contents remain unread
- Focus on user objectives, not implementation

## Step 6. Update user documentation

Must Support:

- The README section describing project-root configuration merging is replaced with a per-project customization section covering: the args file and its host-side location, argument precedence, the caveat that moving or renaming the project directory orphans the args file, and the override guidance (distinctive referenced filename, self-sufficient copy from the assistant's own file, use only when needed)
- The installation and update sections gain a one-line pointer to the template-creation flag

Manual Verification:

- Read the README; confirm the merging description is gone and the new section covers every listed point
- Follow the documented steps in a scratch project; observe they match actual behavior

Prerequisite: Steps 2, 3, 4, and 5

Developer Notes:

- Documentation must match actual behavior exactly; verify each documented claim by hand
- Focus on user objectives, not implementation

Must Support:

- Verification suites cover: args loading and precedence, template creation with no-overwrite, the root-counterpart notice, and both new flags working without container tooling

Manual Verification:
