# Story S6.4 Implementation Steps

Step 1. Enable legacy gate-path migration in the launcher
Must Support:

- Recognition of the exact known-legacy gate path value at launch time
- Rewriting that legacy value to the current gate path before the enablement decision
- Leaving any other pre-set value untouched and enabling the gate directly when no value is set
Manual Verification:
- In a project whose gate path holds the known-legacy value, launch the assistant and observe the configuration now points at the current gate location
- In a project with a custom gate path value, launch the assistant and observe the value is unchanged
- In a project with no gate path set, launch the assistant and observe the gate is enabled directly
Prerequisite: The current gate location must exist in the updated install layout
Developer Notes:
- The rewrite must match the legacy value exactly; similar or related values must not be touched
- Preserve the existing only-when-unset discipline for every non-legacy value
- Focus on the user objective: a gate configured before the relocation keeps working after updating

Step 2. Enable the same legacy rewrite in the installer's update flow
Must Support:

- Applying the identical rewrite rule during update runs
- Repairing the gate path in legacy-configured projects without manual intervention
- Keeping other pre-set values and the unset enable behavior unchanged
Manual Verification:
- Run the installer's update flow in a project holding the legacy gate path and observe the path is repaired
- Run the update flow in a project with a custom gate path and observe no change
- Run the update flow in a project with no gate path and observe the existing enable behavior
Prerequisite: Step 1 (the launcher-side rewrite establishes the shared rewrite rule)
Developer Notes:
- Launcher and installer must behave identically for the same configuration states
- Avoid any behavior change beyond the legacy-value rewrite
- Focus on the user objective: updating the install repairs the gate automatically

Step 3. Enable verification coverage for all three gate-path scenarios
Must Support:

- Assertions that the legacy value is migrated to the current location
- Assertions that other pre-set values stay untouched
- Assertions that an unset value stays unset and the gate enables directly
Manual Verification:
- Run the gate suites and observe every migration case passing
- Temporarily revert the rewrite behavior and observe the suites fail, confirming they guard the migration
Prerequisite: Steps 1 and 2 (the behaviors under test must exist first)
Developer Notes:
- Cover both the launcher path and the installer update path
- Keep the change set limited to gate behavior and its verification; documentation updates belong to the later documentation pass
- Focus on the user objective: confidence the migration is safe for every existing configuration
