# Story S1.5 Implementation Steps

Step 1. Enable reproducible container image build from a pinned base image

Must Support:

- Container image definition building from one specific base image version pinned by tag and digest.
- Successful image build from the project's image definition.
- Base image pin recorded in the technology stack documentation.

Manual Verification:

- Run the image build and confirm it completes without errors.
- Compare the base image reference in the image definition against the pin recorded in the stack documentation and confirm they match.

Prerequisite: None

Developer Notes:

- Keep the recorded pin and the image definition in sync whenever the base image is upgraded.
- Prefer a pinned reference over a moving tag so repeated builds produce the same result.

Step 2. Enable read-write project root access inside the session container

Must Support:

- Full host project root, including the assistant configuration directory, available inside the container at the same path.
- Changes made to project files inside the container persist on the host.

Manual Verification:

- Start a session and confirm the project tree, including the assistant configuration directory, is visible inside the container.
- Edit or create a project file from inside the container and confirm the change appears in the host working tree.

Prerequisite: Step 1

Developer Notes:

- Present the project at the same path used on the host so in-container and host paths stay consistent.
- Avoid copying project files into the image; live access keeps edits synchronized.

Step 3. Enable container engine access from inside the container

Must Support:

- The container engine's control socket reachable inside the session container through group-based permission mapping.
- Engine commands issued inside the container operate on the host engine.

Manual Verification:

- From inside a running session container, run a read-only engine command and confirm it succeeds without permission errors.
- Confirm the launcher reports the engine group mapping during launch, for example via debug output.

Prerequisite: Step 2

Developer Notes:

- Map the engine socket's owning group into the container rather than elevating privileges.
- Verify the mapping works for a non-root runtime user.

Step 4. Enable deterministic session container identity and automatic cleanup

Must Support:

- Session container named deterministically from the workspace identity and the current session.
- Session container removed automatically when the session ends.

Manual Verification:

- Launch a session and confirm the container name reflects the workspace and session identity.
- Exit the session and confirm the session container no longer appears in the engine's container list.

Prerequisite: Step 3

Developer Notes:

- Deterministic naming lets repeat sessions reuse or replace their container predictably.
- Cleanup should also cover abnormal session termination where possible.

Step 5. Enable credential passing at launch only

Must Support:

- API credentials provided from the host environment and forwarded to the container as environment variables at launch.
- No credential values present in any git-tracked file.

Manual Verification:

- Launch a session with a credential set in the host environment and confirm the assistant can use it.
- Search all git-tracked files for the credential value and confirm there are no matches.

Prerequisite: Step 2

Developer Notes:

- Treat the launch environment as the only channel for secrets.
- Never echo secret values in traces or logs.
