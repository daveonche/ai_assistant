# Story S6.2 Implementation Steps

Step 1. Enable launcher-side commit-message gate activation at the relocated hook path
Must Support:

- `_ensure_commit_msg_gate()` in `.agent/ai_assistant.py` configures
  `core.hooksPath` to `.agent/githooks` when the project ships the gate at
  that path and no hook path is configured
- A pre-existing hook-path value set by any other hook manager is never
  overwritten
- An already-active relocated gate is recognized and left unchanged on
  re-launch (idempotent)
- The gate-activation suite (`tests/test_commit_msg_gate_activation.py`)
  asserts the relocated value and passes
Manual Verification:
- In a project with the relocated gate and no hook-path setting, launch the
  assistant and observe `git config core.hooksPath` report `.agent/githooks`
- In a project using another hook framework, launch and observe its
  hook-path setting unchanged
- Launch a second time and observe no configuration change and no error
Prerequisite: The commit-msg hook relocated to `.agent/githooks/` (S6.1, complete)
Developer Notes:
- Activation must remain a repo-local configuration change so behavior is
  identical however the assistant is started
- This step changes the target value, not the activation conditions: the
  only-when-unset safety rule is preserved

Step 2. Enable installer-side gate configuration at the relocated hook path
Must Support:

- `configure_commit_gate()` in `scripts/install.sh` enables `core.hooksPath`
  at `.agent/githooks` during update mode when the fetched reference ships
  the hook
- An existing foreign hook-path value is warned about and left untouched; an
  already-active relocated gate is reported, not reconfigured
- User-facing progress and warning messages state the relocated value
- Installer suites asserting the gate value (e.g., `tests/test_s2_1_step3.py`)
  are updated and pass
Manual Verification:
- Run the installer's update mode in a project with an existing install and
  observe the gate enabled at `.agent/githooks`
- Run update mode in a project with a foreign hook-path setting and observe
  the warning plus untouched configuration
Prerequisite: Step 1 (one consistent gate value across launcher and installer)
Developer Notes:
- Launcher and installer must write the identical value; a mismatch would
  silently deactivate the gate on one of the two paths
- Keep the enable-after-confirmation ordering so an aborted update leaves
  the repository configuration untouched

Step 3. Enable CI commit-subject validation at the relocated hook path
Must Support:

- The commit-subject validation step in `.github/workflows/ci.yml` invokes
  the hook at `.agent/githooks/commit-msg`
- The CI-range suite (`tests/test_ci_commit_subject_range.py`) asserts the
  relocated path and passes
- Hook suites referencing the hook location (e.g.,
  `tests/test_commit_msg_hook.py`) pass, updated only as needed
Manual Verification:
- Push a commit with a non-conforming subject and observe CI reject it via
  the relocated hook
- Observe a green pipeline run on a conforming commit
Prerequisite: The hook relocation from S6.1 (complete); no dependency on
Steps 1-2 (CI invokes the hook file directly)
Developer Notes:
- CI enforcement and the local gate value are independent switches; this
  step only re-points CI at the relocated file

Step 4. Enable consolidated verification of the rewired gate
Must Support:

- All gate-touching suites (launcher activation, installer assertions,
  CI-range, hook) pass in one consolidated run
- No tracked code, CI, or test reference to the legacy `.githooks` hook-path
  value remains (documentation references are the documentation story's scope)
Manual Verification:
- Run the full test suite and observe every test green
- Search the tracked tree for the legacy hook-path value and observe no
  remaining code, CI, or test references
Prerequisite: Steps 1-3
Developer Notes:
- Historical records (implementation status, past commit messages) may
  legitimately retain the legacy value; they are out of scope
