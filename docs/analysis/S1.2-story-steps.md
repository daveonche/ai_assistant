# Story S1.2 Implementation Steps

Step 1. Enable single-command host entry delegation
Must Support:

- The root entry script delegates all lifecycle logic to the assistant launcher by way of the intermediate wrapper script
- The root entry script contains no lifecycle logic of its own
- The delegation chain matches the documented interface contract between the entry script and the launcher
Manual Verification:
- Run the root entry command from the project root and confirm it reaches the assistant launcher
- Confirm the launcher starts (or exits with its own clear prerequisite error), proving the chain is wired end to end
Prerequisite: None
Developer Notes:
- Keep the root entry script a thin pass-through; all behavior lives downstream
- Preserve the documented three-part chain: root entry, wrapper, launcher

Step 2. Enable argument and debug-flag forwarding
Must Support:

- The root entry script forwards the debug flag to the launcher
- All additional assistant arguments supplied by the user are passed through unchanged, in order
- No argument is consumed, reordered, or dropped by the entry chain
Manual Verification:
- Run the entry command with the debug flag and confirm the launcher reports verbose output
- Run the entry command with extra arguments and confirm the launcher receives them unchanged
Prerequisite: Step 1
Developer Notes:
- Forward arguments verbatim; the entry chain should never interpret them
- Verify forwarding with the launcher's own trace output where available

Step 3. Enable executable entry scripts that pass static checks
Must Support:

- Both entry scripts are marked executable so they run directly
- Both scripts pass the project's shell-script static checks with no warnings
- Script style follows the project's shell-script conventions reference
Manual Verification:
- Confirm both scripts are executable in a fresh clone
- Run the project's static checker over both scripts and confirm zero warnings
Prerequisite: Step 1
Developer Notes:
- Record the executable bit in version control so a fresh clone preserves it
- Treat static-check cleanliness as a gate, not a suggestion

Step 4. Enable prerequisite documentation for first use
Must Support:

- The readme documents every host prerequisite required to launch the assistant
- The documented set matches the story's acceptance criteria: the container platform CLI with its compose plugin, the command shell, and the host runtime at its declared minimum version
- Each prerequisite states its purpose (what it is needed for)
Manual Verification:
- Open the readme and confirm the prerequisites section lists each required host prerequisite
- Confirm the listed constraints match the project's declared runtime constraints
Prerequisite: None
Developer Notes:
- Keep prerequisites at the top of the first-use guidance so a new developer sees them before launching
- State only what the host must provide; container-internal tooling is not a host prerequisite

Step 5. Enable dual-mode installation support
Must Support:

- The entry chain works when run from a standalone clone of this repository
- The entry chain works after the core configuration is copied into another project's root
- The readme documents both usage modes with the exact steps for each
Manual Verification:
- Run the entry command from a standalone clone and confirm it reaches the launcher
- Copy the core configuration into a separate project directory, run the entry command there, and confirm it reaches the launcher
- Confirm the readme documents both modes
Prerequisite: Steps 1 and 4
Developer Notes:
- Resolve paths relative to the scripts' own location so the chain works regardless of the caller's directory
- Document the copy-into-project steps, including any permission updates needed in the target project
